## What this is

DuHoc24 — a sample "study-abroad application intake portal" built for a 6-week teaching curriculum. This is the Week 1 checkpoint: static UI only, backed entirely by hardcoded mock data in [`lib/mock-data.ts`](lib/mock-data.ts). There is no real API, database, or auth yet. UI copy and content are in Vietnamese.

The README ([README.md](README.md)) documents the full 6-week roadmap (Gemini chatbot in week 2, Supabase + real forms in week 3, document extraction in week 4, Make.com email automation in week 5, Supabase auth + RLS in week 6). When asked to build a feature from a later week, check the README's checklist for that week's expected scope before implementing.

## Commands

```bash
npm install       # install dependencies (node_modules is not checked in)
npm run dev       # start dev server at http://localhost:3000
npm run build     # production build
npm run start     # run production build
npm run lint      # ESLint (flat config: eslint-config-next core-web-vitals + typescript)
```

There is no test suite configured in this repo.

## Architecture

**Stack**: Next.js 16.3.0 (App Router) + React 19 + TypeScript + Tailwind CSS v4 + shadcn/ui (`base-nova` style, built on Base UI rather than Radix — see [components.json](components.json)).

**Next.js version caveat**: Next.js 16.3 is newer than this model's training data and per [AGENTS.md](AGENTS.md) may have breaking API/convention changes. When `node_modules` is installed, check `node_modules/next/dist/docs/` for the current APIs before writing routing, data-fetching, or config code — don't assume Next 13/14/15 conventions apply unchanged (e.g. layout prop types like `LayoutProps<"/">` in [app/layout.tsx](app/layout.tsx) are generated by Next itself).

**Route structure** (`app/`):
- `/` — landing page ([app/page.tsx](app/page.tsx)): hero, quote-request form, static-UI chatbot widget, highlights, footer
- `/portal` — student document portal, single hardcoded demo student (`currentStudent` in mock-data)
- `/admin` — redirects to `/admin/requests`
- `/admin/*` — admin dashboard sharing [app/admin/layout.tsx](app/admin/layout.tsx), which renders `AdminSidebar`/`AdminMobileNav` from [components/admin/sidebar.tsx](components/admin/sidebar.tsx); add a new admin section by adding both a route under `app/admin/` and an entry in `adminNavItems` in that file
- `/login` does not exist yet — planned for week 6 (Supabase Auth magic link)

**Data layer**: [lib/mock-data.ts](lib/mock-data.ts) is the single source of truth for both types (`DocStatus`, `RequestStatus`, `ServicePackage`, `School`, `AdmissionRequest`, `StudentProfile`, `Conversation`, etc.) and the mock records themselves. Pages import directly from here rather than fetching anything. When wiring up real data in later weeks, these types are the intended shape of the Supabase tables (`requests`, `schools`, `student_profiles`, `conversations`/`messages`).

**Status/tone system**: [components/status-badge.tsx](components/status-badge.tsx) centralizes the mapping from the mock-data status enums (`DocStatus`, `RequestStatus`) to a display tone (gray/yellow/green/red) and label/icon. Add new statuses here rather than inlining color logic in pages.

**Component organization** (`components/`):
- `ui/` — shadcn/ui primitives (button, card, table, select, etc.), generated via the shadcn CLI per [components.json](components.json) — treat as generated, prefer regenerating/extending via shadcn conventions over hand-rewriting
- `landing/`, `portal/`, `admin/` — feature-specific components scoped to one route area
- top-level (`logo.tsx`, `site-header.tsx`, `site-footer.tsx`, `status-badge.tsx`) — shared across route areas

Path alias `@/*` maps to the repo root (see [tsconfig.json](tsconfig.json)); shadcn aliases (`@/components`, `@/components/ui`, `@/lib`, `@/hooks`) follow the same convention.

**Styling**: Tailwind v4 (config lives in [app/globals.css](app/globals.css) via `@theme`, not a `tailwind.config.*` file). Use the `cn()` helper from [lib/utils.ts](lib/utils.ts) (clsx + tailwind-merge) for conditional class merging, matching existing components.

**Env vars**: [.env.example](.env.example) lists Supabase and site-URL variables for future weeks; none are required for `npm run dev` today since everything reads from mock data.
